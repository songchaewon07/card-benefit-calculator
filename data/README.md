# 시드 데이터 안내

`cards.seed.json`의 카드는 대부분 **실제 카드사 상품이 아닌 가상의 카드**입니다 (`source.origin: "manual"`). 혜택 계산 엔진과 UI를 개발/테스트하기 위해 전월실적 조건, 카테고리별 한도, 통합 한도 등 실제 카드에서 흔히 볼 수 있는 구조를 반영해 임의로 작성했습니다.

**예외**: `card-kb-easyall-titanium`(KB국민 Easy all 티타늄카드), `card-shinhan-deepdream-check`(신한카드 Deep Dream 체크), `card-hana-wonder2-freeplus`(하나카드 원더카드 2.0 FREE+), `card-hyundai-check-cashback`(현대카드 체크(캐시백형))는 `source.origin: "crawled"`로, 실제 카드사 공식 페이지를 크롤링해 사람이 검토·반영한 데이터입니다. 다만 네 카드 모두 **완전히 정확하지는 않습니다** — 아래 "실제 카드 반영 시 근사치 처리" 참고.

- 나머지 카드사명/카드명은 모두 가상의 이름입니다.
- 국내 실제 카드사 공식 API/공공데이터 조사 및 크롤링을 통한 검증된 데이터 구축은 **DEV_PROMPTS.md의 Step 2**에서 진행 중입니다.

`subscriptions.seed.json`의 구독료도 참고용 대략적인 값이며, 정확한 최신 가격은 각 서비스에서 별도로 확인이 필요합니다.

## Step 2 진행 상황 (2026-08-19)

1. **공식 API/공공데이터 조사 결과**: 금융감독원(finlife.fss.or.kr), 여신금융협회(gongsi.crefia.or.kr, openapi.crefia.or.kr), 공공데이터포털(data.go.kr)을 조사했으나, "국내 주요 카드사 전체"의 카테고리별 할인율/적립률/전월실적 조건/한도를 다루는 공식 API·공개 데이터셋은 **없었습니다**. 발견한 것은 개별 은행계 카드(산업은행, 우체국)의 상품 개요 API, 여신금융협회의 수수료율/재무 공시, 가맹점 매출 API 정도로, 우리가 필요로 하는 혜택 상세 데이터는 다루지 않습니다. → 크롤링이 보조가 아니라 사실상 주 수단이 되어야 함을 확인했습니다.
2. **카드사 사이트 크롤링 가능 여부**: `../scripts/crawl-cards/targets.ts`에 카드사별 robots.txt 조사 결과를 기록해뒀습니다.
   - 허용(allowed): 신한카드, KB국민카드, **현대카드, 하나카드, 우리카드** — 범용 User-Agent에 카드/혜택 경로가 명시적으로 열려있음
     - 처음에는 현대/하나/우리를 AI 요약만 보고 "불확실"로 분류했으나, robots.txt 원문을 직접 파싱해 재확인한 결과 실제로는 **허용**임을 확인해 정정했습니다. 현대카드·하나카드는 robots.txt에 `User-agent: *`(범용 규칙) 자체가 없고 특정 검색엔진/AI봇 그룹만 있는데, robots.txt 명세상 어떤 그룹에도 매칭되지 않는 User-Agent는 규칙이 적용되지 않아(=제한 없음) 허용으로 판정됩니다. 우리카드는 `User-agent: *`로 `/dcmw/`를 기본 차단하지만 카드 관련 페이지는 명시적으로 재허용하고 있고, GPTBot/ClaudeBot 등 특정 AI 학습봇만 별도로 완전 차단합니다 — 우리 크롤러는 그 이름들에 해당하지 않으므로 `*` 규칙(카드 페이지 허용)이 적용됩니다. (`robots-parser`로 실제 후보 URL에 대해 검증 완료.)
   - 차단(blocked): 삼성카드(robots.txt에서 범용 봇 전체 차단), 롯데카드(자동화 요청 시 연결 차단 추정 — 우회 시도 안 함)
3. **크롤러 골격**: `../scripts/crawl-cards.ts` (`npm run crawl:cards`)에 robots.txt 실시간 재확인, 요청 빈도 제한, 정직한 User-Agent 식별을 갖춘 골격을 구현했습니다.
   - `../scripts/crawl-cards/http-fetch.ts`: 국내 카드사 사이트 특유의 두 가지 문제를 처리하는 fetch 래퍼. (1) 일부 서버(현대카드 등)가 구식 TLS 재협상을 요구해 Node 기본 fetch가 거부하는 경우, `node:https`로 해당 옵션만 완화해 재시도 (인증서 검증은 그대로 유지). (2) 일부 사이트(하나카드 등)가 여전히 EUC-KR로 응답하는데 `Content-Type` 헤더에 charset이 없는 경우가 많아, 응답 본문의 `<meta charset>` 태그를 직접 읽어 인코딩을 감지한 뒤 디코딩 (단위 테스트로 검증).
   - `../scripts/crawl-cards/browser-fetch.ts`: 카드 상세 정보가 자바스크립트로 렌더링되는 사이트(현대카드, 우리카드)를 위해 Playwright 헤드리스 Chromium을 붙였다. `targets.ts`에서 `fetchMethod: "browser"`로 표시된 대상만 이 경로를 타며, 나머지는 그대로 일반 fetch를 사용한다. robots.txt 확인이나 요청 빈도 제한, User-Agent 정책은 fetch 방식과 무관하게 동일하게 적용된다 — 브라우저를 쓴다고 다른 규칙이 적용되진 않는다.
4. **표 추출기 구현 및 실제 페이지 검증** (`../scripts/crawl-cards/extract.ts`): 신한카드·KB국민카드·하나카드 실제 카드 상세페이지를 직접 열어 구조를 확인한 뒤, `<table>`을 caption/헤더/행 단위로 구조화해 추출하고 `<caption>연회비</caption>` 표에서 연회비를 파싱하는 로직을 구현·검증했습니다.
   - 실행 결과 예시: KB "Easy all 티타늄카드" 페이지에서 표 11개(연회비, 전월실적 구간별 한도, A~D 그룹별 할인 카테고리 등)를 정확히 추출, 연회비 30,000원까지 정확히 파싱됨. 신한 체크카드 페이지에서는 통합 적립한도 표(전월실적 구간 3단계)를 정확히 추출, 연회비 표는 없음(체크카드라 실제로 연회비가 없는 것으로 추정)을 올바르게 인식. 하나카드 페이지에서는 표 12개(전가맹점/딜리버리/온라인쇼핑/오픈마켓/택시별 할인율·실적기준·한도)를 정확히 추출.
   - 실행: `npm run crawl:cards [issuerId]` → `scripts/crawl-cards/output/<issuerId>.json`에 저장 (참고용 초안, git에는 커밋하지 않음).
   - **의도적으로 하지 않은 것**: 카테고리별 할인율/적립률을 `Card`/`BenefitRule` 타입으로 완전 자동 변환하는 것. 실제로 확인해보니 카테고리 매핑은 카드마다 자유 문장이거나(신한: "Dream 영역 최대 1% 적립" 같은 prose), 카드사 고유의 복잡한 메커니즘(KB: "전월실적 구간별로 많이 쓴 상위 N개 영역에 자동 캐시백" 같은 동적 로직)으로 되어 있어, 우리 데이터 모델(카테고리 고정 + 고정 한도)에 억지로 끼워 맞추면 조용히 틀린 숫자를 만들어낼 위험이 큽니다. 대신 추출기는 사람이 검토하기 쉬운 구조화된 표(caption + 행) 형태로 정리해주는 데까지만 하고, `data/cards.seed.json`으로의 최종 반영(카테고리 매핑, 단순화 판단)은 사람이 합니다.
5. **현대카드는 헤드리스 브라우저로 뚫었습니다.** 원래 시도한 카드 목록 페이지는 순수 메뉴만 있고 실제 혜택 정보가 없었지만, 체크카드 비교 페이지(`/cpc/cr/CPCCR0621_11.hc?cardflag=C`, robots.txt에서 와일드카드로 허용된 `/cpc/cr/*` 경로)를 렌더링해보니 연회비/기본율/추가율/전월실적/통합한도가 텍스트로 전부 나왔습니다. 다만 `<table>` 태그가 아니라 div/li 레이아웃이라 `extract.ts`의 자동 표 추출기는 0건으로 나오고, 렌더링된 텍스트(`page.innerText`)를 사람이 직접 읽어 반영했습니다. → `card-hyundai-check-cashback`로 반영.
6. **우리카드는 여전히 데이터를 못 얻었습니다 — robots.txt 문제가 아니라 실용적인 문제입니다.** robots.txt가 명시적으로 허용하는 카드 페이지는 `/dcmw/yh1/crd/crd01/M1CRD201S00.do`와 `crd02/M1CRD202S00.do` 두 곳뿐인데, 헤드리스 브라우저로 열어봐도(메인 페이지를 먼저 방문해 세션을 확보한 뒤 재시도해도) 둘 다 "현재 홈페이지 서비스가 원활하지 않습니다"라는 애플리케이션 오류만 나옵니다. 아마 특정 카드를 지정하는 쿼리 파라미터가 더 필요한 것으로 보이는데, 검색으로 찾은 실제로 작동하는 듯한 URL(`M1CRD101S02.do?recomNo=...`)은 robots.txt Allow 목록에 없는 경로라 시도하지 않았습니다 — 허용되지 않은 경로를 우회해서까지 데이터를 가져오지는 않습니다.
7. 삼성카드·롯데카드는 여전히 `blocked` 상태이며 그대로 둡니다(위 1번 각주 참고).

## 실제 카드 반영 시 근사치 처리

### KB Easy all 티타늄카드

`scripts/crawl-cards/output/kb.json`의 추출 결과를 사람이 검토해 `data/cards.seed.json`에 반영했습니다. 연회비(30,000원)와 전월실적 구간별 통합한도(50만원↑ 1.6만원 / 100만원↑ 3.2만원 / 150만원↑ 4.8만원)는 정확합니다. 다만 카테고리 혜택은 두 가지 이유로 **근사치**입니다:

1. **그룹 겹침**: 실제로는 A~D그룹(3%/5%/7%/10%)에 세부 가맹점이 나뉘어 있는데, 우리 카테고리(예: `dining`)에 여러 그룹이 걸치는 경우(일반음식점 A그룹 3% vs 배달앱 D그룹 10%) 과대추정을 피하기 위해 **더 낮은 요율**을 사용했습니다. 각 `BenefitRule.note`에 어떤 그룹을 썼는지, 왜 그런지 기록해뒀습니다.
2. **Auto모드 메커니즘**: 실제 카드는 전월실적 구간에 따라 "많이 쓴 상위 1~3개 영역에만" 캐시백이 적용되는데, 우리 계산 엔진은 입력한 모든 카테고리에 항상 요율을 적용합니다. 즉 사용자가 여러 카테고리에 고르게 소비를 입력할수록 실제보다 혜택이 부풀려질 수 있습니다. 이 점은 `Card.note`(카드 단위 경고)로 남겼고, 카드 선택/결과 화면에 노출됩니다.

### 신한카드 Deep Dream 체크

`scripts/crawl-cards/output/shinhan.json`의 통합적립한도 표(전월실적 20만/40만/80만원 구간 → 5천/1.5만/3만 포인트)를 그대로 반영했습니다. 이 카드는 페이지에 있는 상세 서술(모두드림/더해드림/챙겨드림/DREAM 영역)을 직접 읽고 구조화했습니다 — extract.ts는 이 문장형 정보까지 자동 추출하지 않습니다.

- **DREAM 영역 매핑**: D(할인점)+R(편의점·잡화) → `mart_convenience`, E(영화·커피)의 커피만 → `cafe`, M(이동통신 자동이체) → `telecom`, A(해외) → `other`. 영화(CGV/롯데시네마)는 대응되는 카테고리가 없어 반영하지 않았습니다.
- **의도적으로 보수적(과소평가 쪽)으로 처리한 부분**: (1) 전월실적과 무관하게 전 가맹점에 항상 붙는 '모두드림' 0.2%는 반영하지 않음 — 20만원 미만 소비 시 이 계산기는 0원으로 표시되지만 실제로는 0.2%는 적립됨. (2) DREAM 영역 중 최다이용 1개 영역에 추가로 붙는 '챙겨드림'(0.4%p 추가, 총 1.0%)도 반영하지 않고 그 전 단계인 '더해드림' 요율(0.6%, 전 DREAM 영역에 조건 없이 적용되는 값이라 정확함)만 사용. 카드 단위 `Card.note`에 이 두 가지를 명시했습니다.

### 하나카드 원더카드 2.0 FREE+

`scripts/crawl-cards/output/hana.json`을 반영했습니다. 이 카드는 세 카드 중 가장 단순한 구조입니다 — 카테고리별로 정확한 할인율/실적기준/한도가 표에 명시되어 있어 문장을 해석할 필요가 없었습니다. 다만 두 가지는 근사치입니다:

1. **실적 조건 통일**: 전가맹점 0.8%는 실적 조건이 없고, 배달앱/온라인쇼핑/오픈마켓/택시 4%는 40만원 이상 실적이 필요합니다. 카드 하나에 실적 조건을 하나만 걸 수 있는 우리 모델 특성상 40만원으로 통일했고, 그 결과 40만원 미만 소비 시 전가맹점 혜택도 0원으로 표시됩니다(과소평가).
2. **실적 구간별 한도 중 최저 구간만 사용**: 배달앱/온라인쇼핑/택시 한도는 실적이 늘수록(최대 120만원 이상) 최대 10,000원까지 커지는데, 가장 낮은 구간(40~80만원, 4,000~6,000원)만 반영했습니다(과소평가).
3. 쿠팡은 별도로 2%(실적조건 없음, 통합 5만원 한도)가 적용되는데, 온라인쇼핑 규칙은 오픈마켓/온라인식품쇼핑 표의 4%를 사용해 쿠팡 위주 소비자에게는 다소 과대평가될 수 있습니다 — `BenefitRule.note`에 명시했습니다.

### 현대카드 체크(캐시백형)

헤드리스 브라우저로 렌더링한 텍스트를 사람이 읽고 반영했습니다(표가 아니라 div/li라 자동 추출 대상이 아니었음). 연회비(5,000원)와 통합한도(월 5,000원, 전월실적 30만원 이상)는 정확합니다. 이 카드는 "기본 혜택(전 가맹점 0.3%, 조건 없음) + 추가 혜택(외식·배달앱·편의점·대중교통 3%, 30만원 이상 실적 필요)"이 **더해지는(stack)** 구조라는 걸 페이지 문구("추가 혜택")로 확인하고, 해당 카테고리는 0.3%+3%=3.3%로 합산해 반영했습니다. 근사치인 부분:

1. **실적 조건 통일**: 기본 0.3%는 조건이 없지만, 우리 모델은 카드 하나에 실적 조건을 하나만 걸 수 있어 30만원으로 통일했습니다 → 30만원 미만 소비 시 기본 0.3%도 0원으로 표시(과소평가).
2. **한도 적용 범위**: 실제로는 추가 3%분에만 통합 월 5,000원 한도가 있고 기본 0.3%는 무제한인데, 우리 모델은 카드 전체에 하나의 통합 한도만 걸 수 있어 5,000원 한도를 기본 0.3% 몫까지 포함한 전체 합산에 적용합니다 → 여러 카테고리에 고르게 소비하면 과소평가될 수 있습니다.

같은 접근(구조화 추출 → 사람이 카테고리 매핑·모델 한계 판단 → 애매하면 보수적 선택 → 카드 단위 메커니즘 경고)을 다른 카드에도 반복 적용할 수 있습니다.
